## Где лежит код

  git push -u origin HEAD:main

## Продукт (утверждён владельцем продукта)

Сотрудники 16 районов САО обходят территорию. Увидели люк в плохом
состоянии («неудовлетворительные ОЛХ») — заводят **карточку**: фото ДО +
адрес + район (+ по желанию координаты и комментарий). После устранения
кто-то из того же района прикладывает фото ПОСЛЕ **в ту же карточку**.
Как только ПОСЛЕ загружено, карточка уходит «На проверку» администратору
префектуры: он принимает («Принято») или возвращает с обязательным
комментарием («Возвращено на доработку»). Возвращённая карточка получает
новое фото ПОСЛЕ в той же карточке; прежние фото и решения остаются в
истории; повторное исправление **не увеличивает** «Выявлено».

- Номер карточки: «ОЛХ-001», «ОЛХ-002»… — общая последовательность, 3 знака
  с нулями, после 999 просто растёт.
- Статусы: `detected` (Выявлено), `on_review` (На проверке), `accepted`
  (Принято), `returned` (Возвращено на доработку).
- Фильтры журнала со счётчиками (учитывают выбранный район и период):
  «Все»; «Выявлено (Не исправлено)» = detected + returned; «На проверке» =
  on_review; «Исправлено (Принято)» = accepted.
- «Свод по люкам»: все районы (16, из синхронизированного списка, без
  «Неизвестный район») — Район | Выявлено (неудовлетворительные ОЛХ) |
  Исправлено | На проверке | % исправления, строка «Итого по САО».
  Выявлено — карточки, созданные в периоде; Исправлено — из них принятые
  префектурой; На проверке — из них сейчас на проверке; % = исправлено /
  выявлено × 100, один знак после запятой («66,7%», «70%»), «—» при нуле
  выявленных. Сверху карточки-итоги, период: «За всё время» (по
  умолчанию), «Сегодня», «Неделя», «Месяц», свои даты — по дате создания,
  московское время. «Скачать Excel» выгружает ту же таблицу.
- Дизайн — по макетам владельца «Фотожурнал» и «Свод по люкам» (присланы
  картинками в чате, в репозитории их нет): синее меню слева на компьютере
  / снизу на телефоне, карточки-строки с плитками ДО и ПОСЛЕ, цветные
  статусы. Сначала телефон: работают в поле. Весь интерфейс по-русски, у
  каждой кнопки подпись.

## Роли и вход

Своих паролей у приложения нет — вход тем же логином и паролем, что в
журнале обходов (JiraJura), решение владельца продукта.

- `POST /api/auth/login` → бэкенд вызывает `POST {JIRAJURA_API_URL}/api/v1/auth/login`
  и передаёт `X-Real-IP` с настоящим адресом клиента: JiraJura ограничивает
  попытки входа по этому заголовку, без него все сотрудники выглядели бы
  для неё одним адресом. На проде адрес — `http://api:8000` во внутренней
  docker-сети `jirajura_default`, так что подделать заголовок снаружи нельзя.
- 401/429 от JiraJura передаются как есть (её русский текст). Если
  `must_change_password` — 403 «Сначала смените пароль в журнале обходов…».
- После входа — синхронизация списка районов (`GET /api/v1/districts/` с
  токеном JiraJura; UUID районов JiraJura — первичные ключи и здесь) и
  снимок пользователя. Выдаётся **свой** JWT (HS256, 8 ч), токен JiraJura не
  хранится.
- Роли: `inspector` и `reviewer` JiraJura → сотрудник района (закреплён за
  своим районом; reviewer без района — только просмотр по округу, завести
  карточку не может, с понятным сообщением). `admin` → «Префектура»: видит
  всё, проверяет, может завести карточку с выбором района. Принять/вернуть
  — только префектура. Свод видят все (все районы); журнал сотрудника
  района — только свой район.

## Что сделано

Бэкенд (FastAPI, SQLAlchemy 2 async, Alembic, PostgreSQL 16 без PostGIS):
- таблицы `districts`, `users`, `cards`, `card_photos` (kind before/after,
  attempt: 0 у ДО, 1, 2… у попыток ПОСЛЕ), `card_events` (created /
  after_uploaded / accepted / returned), `audit_log`; миграция `0001_initial`;
- эндпоинты: `/api/auth/login`, `/api/auth/me`, `/api/districts`,
  `/api/cards` (создание, список с фильтрами и счётчиками), `/api/cards/review-queue`,
  `/api/cards/{id}`, `/api/cards/{id}/photos?kind=before|after`,
  `/api/cards/{id}/accept`, `/api/cards/{id}/return`, `/api/summary`,
  `/api/summary.xlsx`, `/api/health`;
- фото: белый список расширений, лимит размера, превью через Pillow
  (HEIC — pillow-heif), хранение на диске (`UPLOAD_DIR`, том);
- в проде API не стартует с ключом-заглушкой (`SECRET_KEY` короче 32
  символов, содержит «change-me» или равен dev-ключу).

Фронтенд (React + TS + Vite + Tailwind v4 + react-query, PWA): страницы
«Вход», «Фотожурнал», карточка, «Зафиксировать нарушение», «Проверка»
(префектура), «Свод»; загрузка фото с повторами.

Инфраструктура (последний коммит, см. ниже «Не проверено»):
`docker-compose.prod.yml` (сервисы `db`, `luki-api`, `luki-web`, без
опубликованных портов; api и web во внешней сети `jirajura_default` с
алиасами `luki-api`/`luki-web`, БД — только во внутренней сети),
`docker-compose.yml` для локального запуска, Dockerfile'ы, `frontend/nginx.conf`
(web на 8080, `/api/` и `/uploads/` → `luki-api:8000` через resolver),
`backend/docker-entrypoint.sh` (миграции на каждом старте),
`deploy/scripts/backup.sh`, `.env.example`, CI `.github/workflows/ci.yml`.

Решения, которые не видны из кода с первого взгляда (есть в комментариях):
- сервисы названы `luki-api`/`luki-web`, а не `api`/`web`: имя сервиса
  регистрируется как DNS-имя во всех его сетях, и второй `api` в
  `jirajura_default` перехватывал бы запросы к API журнала обходов;
- httpx-клиент к JiraJura с `trust_env=False`: иначе docker может
  подложить HTTP(S)_PROXY, который не видит внутреннюю сеть;
- nginx web доверяет `X-Real-IP` только от адресов docker-сетей
  (`set_real_ip_from`), порт 8080 наружу не опубликован.
